# Changelog

Written for Consumers: what a mod building against Example Module can use, or will see change. A published version never changes: a fix is the next patch (`docs/agents/releases.md`).

## Unreleased

- `libworks-runtime` 0.1.12: libworks-gametest's `GalleryCheck.MAX_SCENES` is 24, up from 16, so `builds` and `withPack` take a gallery of up to 24 scenes.
- `libworks-runtime` 0.1.11: libworks-gametest's `GalleryCheck.MAX_SCENES` is 16, up from 12, so `builds` and `withPack` take a gallery of up to 16 scenes, such as Voidworks' 13; `Layout.ONE_ROW` holds as many.
- `libworks-runtime` 0.1.10: libworks-gametest's `GalleryCheck` checks a gallery laid in rows (#31). `GalleryCheck.Layout(perRow, rowDepth)` lays each row's scenes a plot east of the last and each row `rowDepth` blocks north of the one before, refusing rows closer than a plot is deep, and `builds(helper, modId, origin, layout, scenes)` follows it in its key blocks, the plots it force-loads and those it clears; `builds` without one checks a single row, as before. `GalleryCheck.withPack(helper, modId, origin, layout, plots, steps)` is the frame `builds` runs in, public for a Module's per-scene tests: the pack on over the plots, loaded, the test's own steps added to the sequence with an operator player's source to build from, then the plots cleared and the pack off, passing or failing; it returns the test's sequence for the test to end. Clearing runs the pack's `<modid>:gallery/clear` on each plot first when it has one, which `GalleryPack.clear(modId)` names (`docs/runtime.md`). A Module that copied the frame, as Pipeworks and Voidworks did, can drop its copy.
- `libworks-plugin` 0.4.2: `module-ci.yml` at `plugin-v0.4.2` has a `textures` job that runs `python3 scripts/build-textures.py --check`, with Pillow, when the Module has that script, and does nothing otherwise, so a Module drops its own texture job when it moves to that tag (#27). The template ships `NOTICE` with the preamble every Module's shares and no entries, and a commented `REUSE.toml` override stanza for third-party art such as Malcolm Riley's unused textures, which needs `LICENSES/CC-BY-4.0.txt` once uncommented.
- `libworks-plugin` 0.4.1: `upload` records each upload a site takes beside the jar, in `<archives_name>-<version>.uploads.json` in `~/.m2` with the site's id for it and when, and refuses a site already recorded before contacting it, so a `-Psite=curseforge` retry no longer uploads a version again while its first file waits in CurseForge's review, which the website's listing doesn't show (#22). The record only knows the machine that uploaded. A site's entry is removed by hand only when that site rejected the file or never showed it, and `-PdryRun` shows what the record holds (`docs/agents/releases.md`).
- `libworks-plugin` 0.4.0, breaking: the plugin declares the Module's `~/.m2` repository, `exclusiveContent` for the whole `io.github.5thlayer` group, so every 5thlayer module resolves from `~/.m2` alone and `~/.m2` serves nothing else (`docs/plugin.md`, #18). A Module that takes it deletes its own `~/.m2` repository, `mavenLocal { content { … } }` or `exclusiveContent { forRepository { mavenLocal() } … }`: the plugin refuses either, naming it. The template's `build.gradle` has none.
- The template's game-test code never ships (libworks ADR 0011, #17): `ExampleLibGameTests`, `CodeGameTest`, the test classes and `structure/gametest/platform.nbt` are in the `gametest` source set, and the jar holds none of them. `ExampleLibGameTests` is an `@EventBusSubscriber` that registers from `FMLConstructModEvent`, so `ExampleLib` names no game-test code, and nothing gates it: it registers in every one of the Module's own runs.
- The template's game-test code never ships (ADR 0011, #17): `ExampleLibGameTests`, `CodeGameTest`, the test classes and `structure/gametest/platform.nbt` are in the `gametest` source set, and the jar holds none of them. `ExampleLibGameTests` is an `@EventBusSubscriber` that registers from `FMLConstructModEvent`, so `ExampleLib` names no game-test code, and nothing gates it: it registers in every one of the Module's own runs.
- `libworks-plugin` 0.4.0, breaking: `libworksGametest` is on the `gametest` source set's compile classpath and no longer `main`'s, so `src/main` code that names libworks-gametest stops compiling, and `buildGametestStructures` writes into `src/gametest/resources` (ADR 0011, #17). `docs/plugin.md` lists what a Module moves and deletes.
- `libworks-runtime` 0.1.9: a Module's Gallery pack, `gallery_pack/` in its jar, a datapack of functions only that builds a working scene of each feature (ADR 0010, #29). `GalleryPack.register(modBus, modId)` offers it in the Data Packs screen, never on by default. libworks-gametest's `GalleryCheck.builds(helper, modId, origin, scenes)` is the gallery game test: the pack is offered and off, every gallery function loads, the build runs every command without failing, naming the one that does, and each scene's key block stands in its plot. `docs/runtime.md` holds the layout every gallery follows.
- The template says Module where it said Library, after FactoryWorks' glossary (ADR-0115, ADR-0128): its display name placeholder is `Example Module`, which `fill-template.sh` replaces, and ADR 0004 is `0004-a-modules-dev-and-game-test-packs-never-ship.md` (5thlayer/skillworks#14).
- The template starts with the Works tab: `libworks { runtime = '0.1.8' }`, the `libworks` dependency in `neoforge.mods.toml`, an empty `WorksTabContents` listener on `WorksTab.KEY`, and a `CreativeTabTests` game test. Until the Library lists an item in its `WORKS_TAB_ORDER` it checks that the Library registers none, so the first item fails until it is listed; then it runs `WorksTabCheck.inOrder` and `noOtherTab` (#26).
- `libworks-plugin` 0.3.0, breaking: a Module whose `runtime` is 0.1.8 or later gets `libworks-gametest` at the runtime's range on `libworksGametest`, which `compileOnly` and `localRuntime` extend, so its game tests call `WorksTabCheck` with no dependency of their own (`docs/plugin.md`, #25). Its `~/.m2` repository must let `libworks-gametest` through, an edit to its build, so the bump is a minor (ADR 0001).
- `libworks-plugin` 0.2.2: `writeGameTestServerCommand` writes the game test server's whole command line, classpath included, to `build/moddev/gameTestServerRunCommand.txt`, so the game tests can run again without Gradle, as skillworks' `gametest-loop` runs them (`docs/plugin.md`).
- `libworks-runtime` 0.1.8: `libworks-gametest` 0.1.8, published beside the runtime at its version: `WorksTabCheck.inOrder(helper, modId, order)` and `WorksTabCheck.noOtherTab(helper, modId)` are the Works tab game test, so a Module's `CreativeTabTests` names only its mod id and its items' order (`docs/runtime.md`, ADR 0008, #25). A Module takes it `compileOnly` and `localRuntime`, never by jar-in-jar.
- `libworks-runtime` 0.1.7: `GhostScreen.ghostAt(mouseX, mouseY)` is the ghost under the mouse that EMI is handed, `ghosts()`' by default; a screen with a ghost beyond them, such as one it draws as the item itself, overrides it to find that one too (`docs/runtime.md`, #23). A screen's own `ghostAt(double, double)` now overrides it, so it must be public and return `Optional<Ghost>`.
- `libworks-runtime` 0.1.6: a screen that implements `io.github._5thlayer.libworks.ghost.GhostScreen`, whose one method returns its `Ghosts`, has its ghosts in EMI with nothing else to register: the runtime's own `@EmiEntrypoint` offers the ghost under the mouse as EMI's hovered stack, which the recipe and usage keys answer, and which is not clickable, so a left click on a ghost reaches the empty slot under it (`docs/runtime.md`, ADR 0007, #23). A Module drops its own EMI stack provider for those ghosts. The runtime builds against EMI 1.1.24 and runs without it.
- `libworks-runtime` 0.1.5: `io.github._5thlayer.libworks.machine.FluidContainers` gives a machine drain and fill slots for any item with NeoForge's fluid item capability, not only buckets: `drain` and `fill` move one whole container between a tank and the item, or nothing while the tank has too little room or too little of the fluid, or the output no room, for all of it, and `holds` and `takes` are the slots' checks (`docs/runtime.md`, #21). It is Wireworks' `FluidContainers`, made public, except that `fill` draws only the fluid it names, where Wireworks' drew whatever the tank held.
- `libworks-runtime` 0.1.4: `MachineDraw.fluidTooltip` has an overload that takes a tank's title and shows it first, above the fluid's name, or "Empty", and the amount, so a machine with named tanks words an empty one as every other machine does.
- `libworks-runtime` 0.1.3: `MachineDraw.gauge` writes a gauge's amount only when a full gauge's label would fit, so a gauge narrower than its capacity's label, such as Craftworks' fluid boxes, shows none at any fill, where it showed one only while the amount was short.
- `libworks-runtime` 0.1.2: `io.github._5thlayer.libworks.machine` gives the Modules' machines one stand-in screen look and one Jade view (`docs/runtime.md`, ADR 0006, #20). `machine.client.MachineDraw` draws the panel with its slots' recesses and ghosts, bars, fluid gauges and their tooltip, and text cut to fit; `GhostDraw.tooltip` shows a ghost's item tooltip. `machine.jade.MachineReport`, `MachineItems` and `MachineTanks`, with a `Tank` each, are the Jade providers a Module's own `@WailaPlugin` builds and registers; the runtime builds against Jade 26.1.11 and runs without it.
- `libworks-plugin` 0.2.1: `check` runs `checkPlaysAlone`, which fails when the Module ships an id, a data or assets folder, or a namespace string of another FactoryWorks Module, or requires one in `neoforge.mods.toml` (FactoryWorks ADR-0127, ADR 0005, #19). The plugin holds the one list of Modules, Gearworks and Voidworks included. A Module drops its own copy of the scan.
- `libworks-plugin` 0.2.0, breaking: the plugin adds a `gametest` source set to the mod, which the dev runs load and the jar leaves out, and sets `libworks.run` to each run's name (ADR 0004, #6). A Module that adds `sourceSet sourceSets.gametest` to its mod itself is refused: delete the line.
- The template's `DevPacks`, in `src/gametest/java`, switches on `dev_pack/` in the `client` run and `gametest_pack/` in `gameTestServer` when the Library has one, and its game test checks the template's own game-test pack (ADR 0004, #6).
- `libworks-runtime` 0.1.1: `io.github._5thlayer.libworks.ghost` shows the faded item an empty slot would take (`docs/runtime.md`, #16). A screen owns a `Ghosts`, registers its slots (`add(Slot)` for every item the slot's `mayPlace` takes) or any screen position with its candidates, draws `shown(millis)` with `ghost.client.GhostDraw.draw`, and asks `at(mouseX, mouseY, millis)` what is under the mouse for EMI and JEI. `Ghosts.of(SizedIngredient)` gives an ingredient's members at its count, and a position cycles its candidates once a second.
- `libworks-plugin` 0.1.2: `buildGametestStructures` refuses, naming the file, to overwrite a `platform.nbt` the Module committed that differs from the default one.
- `libworks-plugin` 0.1.2: the plugin no longer leaves an unfiltered `mavenLocal()` repository on the Module.
- `libworks-plugin` 0.1.2: `neoforge.mods.toml` can name the runtime's range as `${libworks_runtime_range}`, such as `[0.1.0,0.2)`, when `runtime` is set.
- `libworks-plugin` 0.1.2: `libworksUpstreams` lists the runtime as `5thlayer/libworks runtime-v<version> :runtime` when `runtime` is set, and `module-ci.yml` publishes `libworks-runtime` from that tag, so a Module nesting it builds in CI.
- `libworks-plugin` 0.1.1: `neoforge.mods.toml` can name an upstream's range as `${<name>_range}`, such as `versionRange = "${groundworks_range}"`.
- `libworks-plugin` 0.1.1: `upstream('<name>') { optional = true }` puts the Library on a `localRuntime` configuration the dev runs load, leaving the published jar, pom and module metadata free of it.
- `libworks-runtime` 0.1.0, a runtime mod (id `libworks`) a Module nests, FML loading the newest copy once. It registers the shared creative tab `libworks:works`, titled "Works", whose key is `WorksTab.KEY`, and holds `GuardedResourceHandler`, a `DelegatingResourceHandler` whose slot-less insert and extract honour a subclass's per-slot refusals (`docs/runtime.md`, #8).
- `libworks-plugin` 0.1.0, the Module convention plugin `io.github.5thlayer.libworks.module` (ADR 0003, #11): the shared build (Java 25, ModDevGradle, game test report check, jar licensing, `neoforge.mods.toml` expansion, an immutable `publishToMavenLocal` refused under `-PsiblingBuilds`) and a `libworks { }` block. `upstream('<name>') { range; tagPrefix; repo }` requires a Library strictly in its range, preferring the lower bound, and fails when a `-PsiblingBuilds` checkout (`-P<name>Dir`, `~/minecraft_mods/<name>` by default) falls outside it; `libworksUpstreams` prints `<repo> <tag> <version>` per upstream for CI. `runtime = '<version>'` nests `libworks-runtime` from `<version>` up to the next minor (`0.1.3` gives `[0.1.3,0.2)`), as ADR 0001 has a breaking change bump the minor below 1.0. `tagPrefix` defaults to `<archives_name>-v`.
- The plugin bundles the release, upload and game test structure scripts (#12): `sh ./gradlew release -PreleaseVersion=<v> [-Pupload]` tags `<tagPrefix><v>` and is refused under `-PsiblingBuilds`; `upload -PreleaseVersion=<v> [-PdryRun] [-Psite=<site>]` checks the jar for the Module's LICENSE, NOTICE and every file under LICENSES/; `buildGametestStructures` writes the default platform. A Module keeps no `scripts/` of its own.
- The reusable workflow `5thlayer/libworks/.github/workflows/module-ci.yml@plugin-v<version>` replaces a Module's copied `ci.yml` (#13): it builds the plugin from its tag and each `libworksUpstreams` Library from its tag into the runner's `~/.m2`, then runs `build`, `runGameTestServer` (uploading the report) and REUSE lint.
- The template is a build that applies the plugin (#14): `fill-template.sh` gives a Library `id 'io.github.5thlayer.libworks.module' version '<plugin_version>'` resolved from `~/.m2`, a `ci.yml` calling `module-ci.yml` at `plugin-v<plugin_version>`, and no `plugin/`, `runtime/` or `scripts/`.
